# Data Model Design
- **Models Created**: `Project` and `Task`.
- **Fields**:
    - `Project`: `name`, `description`, `owner`, `created_at`.
    - `Task`: `title`, `description`, `project`, `priority`, `status`, `due_date`, `created_at`, `updated_at`.
- **Relationships**:
    - `Task.project`: A `ForeignKey` to `Project`. This creates a one-to-many relationship where a project can have multiple tasks. `on_delete=models.CASCADE` was chosen so that if a project is deleted, all its associated tasks are also deleted. This keeps the database clean and avoids orphaned tasks.
    - `Project.owner`: A `ForeignKey` to the `User` model. This assigns ownership of a project to a user. `on_delete=models.CASCADE` means if a user is deleted, their projects (and by extension, their tasks) are also deleted.
- **Constraints**:
    - `UniqueConstraint(fields=['project', 'title'], name='unique_task_title_in_project')` in the `Task` model ensures that no two tasks within the same project can have the same title. This prevents duplicate tasks.
    - `ordering = ["name"]` in `Project` and `ordering = ["status", "-priority", "due_date", "-created_at"]` in `Task` provide default sorting for querysets, which is useful for consistent presentation.
- **Seeding Data**:
    - A superuser was created to own the projects.
    - Two projects were created: "Website Redesign" and "Mobile App Development".
    - Several tasks were created for each project with different priorities, statuses, and due dates to simulate a real-world scenario.
    - A duplicate task was attempted to be created to test the `UniqueConstraint`.

# Assignment 4 - Django Views Implementation

## Why I Wrote Two Views
- **HttpResponse View (task_stats)**: Demonstrates manual HTML construction without Django's template system. This shows the low-level approach where you have complete control over the HTML output but must handle everything manually.
- **render() View (task_board)**: Uses Django's template system with context passing. This is the preferred Django approach as it separates logic from presentation and enables template inheritance.

## Differences Between HttpResponse and render()
- **HttpResponse**: Returns raw HTML strings constructed in Python. Requires manual HTML escaping and styling. Good for simple responses or API endpoints. Less maintainable for complex pages.
- **render()**: Uses Django templates with context dictionaries. Supports template inheritance, filters, tags, and automatic HTML escaping. More maintainable and follows Django best practices.

## URL and Template Decisions
- **Separate URLs**: Created distinct URLs (/tasks/stats/ and /tasks/) to clearly demonstrate both approaches working independently.
- **Template Inheritance**: Used base.html with {% block %} structure to maintain consistent navigation and styling across all pages.
- **{% for %} with {% empty %}**: Implemented in all list templates to gracefully handle empty querysets with user-friendly messages.
- **Context Strategy**: Passed multiple querysets in render() view to organize tasks by status, enabling the kanban board layout.

## Key Learning Points
- HttpResponse requires manual work but gives complete control
- render() leverages Django's powerful template system for cleaner, more maintainable code
- Both approaches can use the same underlying data and business logic
- Template inheritance eliminates code duplication across pages

# Assignment 6 - Base CBVs vs Generic CBVs Implementation

## Difference Between Base CBVs and Generic CBVs

### Base CBVs (inheriting from View)
- **Manual Implementation**: Must implement get(), post(), etc. methods explicitly
- **Explicit Queries**: Write all database queries manually (Task.objects.count(), Task.objects.filter())
- **Custom Context**: Create context dictionaries with custom variable names
- **Full Control**: Complete control over request/response cycle and data processing
- **More Code**: Requires more boilerplate code but maximum flexibility

### Generic CBVs (ListView, DetailView, CreateView)
- **Automatic Implementation**: Django handles common patterns automatically
- **Built-in Queries**: Automatic queryset handling based on model attribute
- **Standard Context**: Uses default context names (object_list, object) or custom context_object_name
- **Convention-based**: Follows Django conventions for template naming and behavior
- **Less Code**: Minimal code required, built-in pagination, form handling, etc.

## Why Generic Views Reduce Boilerplate

### Before (Function-based or Base CBV):
```python
def task_list(request):
    tasks = Task.objects.all().order_by('status', '-priority')
    paginator = Paginator(tasks, 10)
    page = request.GET.get('page')
    tasks = paginator.get_page(page)
    context = {'tasks': tasks}
    return render(request, 'tasks/task_list.html', context)
```

### After (Generic ListView):
```python
class TaskListView(ListView):
    model = Task
    paginate_by = 10
    ordering = ['status', '-priority']
```

- **Automatic pagination**: No need to write pagination logic
- **Queryset handling**: Django automatically queries Task.objects.all()
- **Context creation**: Automatic context with 'object_list' or custom name
- **Template selection**: Follows convention (app/model_list.html) or custom template_name

## Why Refactoring URLs Improves Maintainability

### Before Refactoring (all URLs in project-level):
- All app URLs mixed together in main urls.py
- Hard to find and modify specific app routes
- URL naming conflicts between apps
- Difficult to reuse apps in other projects

### After Refactoring (with include()):
- **Separation of Concerns**: Each app manages its own URLs
- **Modularity**: Apps are self-contained with their URL patterns
- **Namespace Support**: Prevents URL name conflicts
- **Reusability**: Apps can be easily moved between projects
- **Maintainability**: Easier to find and modify URLs for specific features
- **Team Development**: Different developers can work on different apps independently

### URL Structure Benefits:
```python
# Project-level: Clean and focused
urlpatterns = [
    path('admin/', admin.site.urls),
    path('', home, name='home'),
    path('tasks/', include('tasks.urls')),  # Delegates to app
]

# App-level: Complete control over app routes
urlpatterns = [
    path('cbv/', TaskListView.as_view(), name='task_list_cbv'),
    path('cbv/stats/', TaskStatsView.as_view(), name='task_stats_cbv'),
]
```

# Assignment 7 - Search/Filtering and Aggregations Implementation

## Filtering vs Aggregation Concepts

### Filtering (Narrowing Data)
- **Purpose**: Reduces the number of rows returned from a queryset based on conditions
- **Django Methods**: `.filter()`, `.exclude()`, `.get()`
- **SQL Equivalent**: WHERE clause conditions
- **Our Implementation**: Multi-field search using Q() objects across task title, description, and project name
- **Result**: Returns a subset of Task objects that match the search criteria

### Aggregation (Summarizing Data)
- **Purpose**: Computes summary values across groups of data (counts, sums, averages)
- **Django Methods**: `.count()`, `.aggregate()`, `.annotate()` with `Count()`, `Sum()`, `Avg()`
- **SQL Equivalent**: GROUP BY clauses with aggregate functions
- **Our Implementation**: Overall totals and grouped counts by status, priority, and project
- **Result**: Returns computed summary statistics rather than individual objects

## Specific Aggregation Summaries in Our Project

### Overall Aggregations (Single Values)
- **Total Tasks**: `Task.objects.count()` - Simple count of all tasks in system
- **Completed Tasks**: `Task.objects.filter(status=Status.DONE).count()` - Count with filter condition
- **Overdue Tasks**: Complex filter with date comparison and status exclusion for actionable overdue items

### Grouped Aggregations (Counts by Category)
- **Tasks by Status**: `Task.objects.values('status').annotate(count=Count('id'))` - Groups tasks by status field and counts each group
- **Tasks by Priority**: `Task.objects.values('priority').annotate(count=Count('id'))` - Groups by priority level with count
- **Tasks by Project**: `Project.objects.annotate(task_count=Count('tasks'))` - Counts tasks per project using reverse relationship

## Query Optimization Techniques Used
- **select_related('project')**: Prevents N+1 queries when displaying task project names in list view
- **Q() Objects**: Enables OR logic for multi-field search across unrelated fields
- **Lazy Evaluation**: QuerySets not executed until template iteration, allowing efficient chaining of filters and annotations

# Assignment 8 - Forms, GET vs POST, and FBV vs CBV Implementation

## CSRF Protection
- **What is CSRF**: Cross-Site Request Forgery is an attack where malicious websites trick users into submitting unintended requests to a trusted site where they're authenticated.
- **Why CSRF Protection is Needed**: Without it, an attacker could create a fake form that submits to your Django app using the victim's cookies/session, performing actions without their consent.
- **Django's CSRF Token**: Django generates a unique, secret token for each session that must be included in POST forms via {% csrf_token %}, preventing unauthorized form submissions.
- **How It Works**: Django checks that the CSRF token in the POST request matches the token stored in the user's session; if they don't match, the request is rejected with a 403 error.

## Django Form Submission Process
- **Step 1 - Form Rendering (GET)**: View instantiates an empty form and renders it in a template with {% csrf_token %} included automatically.
- **Step 2 - User Submission (POST)**: User fills out form and submits; browser sends POST request with form data and CSRF token to server.
- **Step 3 - CSRF Validation**: Django middleware checks CSRF token before the view is even called; rejects request if token is invalid.
- **Step 4 - Form Validation**: View receives POST data, binds it to form object, calls is_valid() which runs field validators and clean methods.
- **Step 5 - Processing**: If valid, view saves/processes data and redirects; if invalid, re-renders form with bound data and error messages.
- **Step 6 - Success Handling**: After successful submission, redirect to success page using redirect() or success_url to prevent duplicate submissions on refresh.

## Function-Based Views vs Class-Based Views for Forms

### FBV Pros
- **Explicit Control**: Every step is visible - you write if request.method == 'POST' and handle each case manually.
- **Easier to Understand**: Linear flow is straightforward for beginners; clear separation of GET and POST logic.
- **Flexibility**: Can easily handle complex logic, multiple forms, or non-standard workflows without fighting framework conventions.

### FBV Cons
- **More Boilerplate**: Must manually check request method, instantiate forms, validate, save, and redirect each time.
- **Code Duplication**: Similar patterns repeated across multiple views (form instantiation, validation checking, error handling).
- **Less Reusable**: Hard to extend or override specific behaviors without copying entire function.

### CBV Pros
- **Less Code**: Generic views like CreateView handle form instantiation, validation, saving, and redirects automatically.
- **Reusability**: Can inherit from base classes and override only specific methods (e.g., form_valid() for custom success logic).
- **Convention-Based**: Follows Django patterns with automatic template naming, context variables, and success URL handling.

### CBV Cons
- **Steeper Learning Curve**: Must understand method resolution order (MRO), which methods to override, and Django's class hierarchy.
- **Less Explicit**: Logic is hidden in parent classes; harder to debug and understand what's happening behind the scenes.
- **Overkill for Simple Cases**: For very simple forms or unique workflows, writing a CBV can be more complex than a straightforward FBV.

## When to Use GET vs POST

### Use GET When:
- **Reading/Searching**: Filtering, searching, or querying data without modifying server state (e.g., search forms).
- **Bookmarkable URLs**: Query parameters appear in URL (?q=search), allowing users to bookmark and share results.
- **Idempotent Operations**: Multiple identical GET requests should return the same result without side effects.
- **No Sensitive Data**: GET parameters are visible in URL, browser history, and server logs - never use for passwords or private info.

### Use POST When:
- **Creating/Modifying Data**: Any operation that changes database state (creating tasks, updating profiles, deleting records).
- **Sensitive Information**: Passwords, credit cards, or personal data that shouldn't appear in URLs or logs.
- **Non-Idempotent Operations**: Actions that shouldn't be repeated accidentally (e.g., submitting a payment or creating a resource).
- **Large Data**: POST body has no size limit unlike GET URL parameters which browsers/servers may truncate.
- **CSRF Protection Required**: POST forms can include CSRF tokens to prevent unauthorized submissions; GET forms cannot be CSRF-protected.

# Assignment 9 - JSON APIs and Server-Side Chart Generation

## What is a JSON API?

### Definition and Purpose
- **JSON API**: An HTTP endpoint that returns data in JSON (JavaScript Object Notation) format instead of HTML
- **Purpose**: Enables data exchange between systems (frontend ↔ backend, mobile apps, third-party integrations)
- **Structure**: Typically returns structured data with `count` and `results` keys for collections
- **RESTful Principles**: Uses URL patterns to represent resources (e.g., `/api/tasks/`, `/api/stats/`)

### Why JSON APIs Matter
- **Separation of Concerns**: Data layer decoupled from presentation - API serves data, frontend renders it
- **Multiple Consumers**: Same API can serve web apps, mobile apps, desktop apps, and other services
- **Machine-Readable**: JSON is easy for programs to parse and generate (unlike HTML meant for humans)
- **Framework-Agnostic**: Any language/framework can consume JSON APIs (Python, JavaScript, Swift, Kotlin, etc.)

## HttpResponse vs JsonResponse

### HttpResponse (Generic Response)
- **Content Type**: Defaults to `text/html` but can be set to any MIME type (`text/plain`, `image/png`, `application/pdf`)
- **Manual Serialization**: You must convert Python data to strings manually
- **Use Cases**:
  - HTML pages: `HttpResponse("<html>...</html>")`
  - Plain text: `HttpResponse("ok: true", content_type="text/plain")`
  - Binary data: `HttpResponse(image_bytes, content_type="image/png")`
- **Flexibility**: Complete control over content and headers but requires more manual work

### JsonResponse (Specialized for JSON)
- **Content Type**: Automatically sets `Content-Type: application/json`
- **Automatic Serialization**: Converts Python dicts/lists to JSON automatically using `json.dumps()`
- **Safe Mode**: By default, only allows dicts (not lists) as top-level objects to prevent security issues
- **Use Cases**:
  - API endpoints: `JsonResponse({'count': 10, 'results': [...]})`
  - AJAX responses: `JsonResponse({'success': True, 'message': 'Saved!'})`
- **Convenience**: Less code and automatic handling of JSON encoding

### Key Difference Example
```python
# HttpResponse (manual)
data = {'ok': True}
return HttpResponse(json.dumps(data), content_type='application/json')

# JsonResponse (automatic)
return JsonResponse({'ok': True})
```

### MIME Type Impact
- **Browser Rendering**: `application/json` triggers browser's JSON formatter/viewer
- **API Clients**: Libraries like `requests` or `urllib` check Content-Type to parse response correctly
- **JavaScript**: `fetch()` and `$.ajax()` automatically parse `application/json` responses to objects

## Server-Side Chart Data Flow

### Architecture Overview
**Django View → API Request → JSON Parsing → Matplotlib → PNG Response**

### Step-by-Step Process

1. **Chart View Receives Request**
   - User requests `/api/chart.png`
   - Django routes to `task_chart_png(request)` view

2. **Build API URL**
   - Use `reverse('task_stats_api')` to get relative path (e.g., `/tasks/api/stats/`)
   - Use `request.build_absolute_uri(api_path)` to create full URL (e.g., `http://127.0.0.1:8000/tasks/api/stats/`)
   - This allows view to call its own server's API

3. **Fetch JSON from API (Server-Side)**
   - Use `urllib.request.urlopen(api_url)` to make HTTP GET request to our API
   - **Important**: This is server-to-server, NOT JavaScript in browser
   - Python code fetches JSON before sending response to browser

4. **Parse JSON Data**
   - Use `json.load(response)` to convert JSON string to Python dict
   - Extract needed data: `data['status_breakdown']`, `data['overall']`, etc.
   - This data came from Django ORM queries in the API view

5. **Generate Chart with Matplotlib**
   - Create figure: `fig, axes = plt.subplots(2, 2, figsize=(14, 10))`
   - Plot data: pie charts for status, bar charts for priority, text for stats
   - Style with Illinois colors and formatting

6. **Convert Chart to PNG Bytes**
   - Create buffer: `buffer = io.BytesIO()`
   - Save figure to buffer: `plt.savefig(buffer, format='png', dpi=100)`
   - Get raw bytes: `buffer.getvalue()`

7. **Return as HttpResponse**
   - Return: `HttpResponse(buffer.getvalue(), content_type='image/png')`
   - Browser receives PNG image and displays it
   - Can be embedded in HTML: `<img src="{% url 'task_chart_png' %}">`

### What the Chart Shows
- **Status Distribution**: Pie chart showing proportion of tasks in To Do / In Progress / Done
- **Priority Breakdown**: Bar chart showing count of Low/Medium/High priority tasks
- **Overall Statistics**: Text display of total tasks, completed, pending, overdue, and completion rate
- **Top Projects**: Horizontal bar chart of projects with most tasks

### Why This Architecture?
- **No JavaScript Required**: Chart generation happens on server, browser just displays image
- **Consistent Styling**: Matplotlib renders same way regardless of browser
- **API Reusability**: Chart view consumes same API that could be used by mobile apps or JavaScript
- **Separation of Concerns**: Data aggregation (API) separated from visualization (chart view)
- **Simple Client**: Browser only needs to support `<img>` tags, no chart libraries needed

## Function-Based vs Class-Based API Views

### FBV API (tasks_api, task_stats_api)
- **Explicit Control**: Direct function that returns JsonResponse
- **Simple Pattern**: Check request.method if needed, query database, return JSON
- **Less Abstraction**: Clear what's happening in each line of code

### CBV API (TaskStatsAPIView)
- **Inheritance**: Extends `View` class and implements `get(self, request)` method
- **Reusability**: Can override dispatch(), add mixins, implement post/put/delete easily
- **Consistency**: Follows Django's CBV pattern for better organization
- **Scalability**: Easier to add authentication, permissions, throttling as methods

### When to Use Each
- **FBV**: Simple APIs with minimal logic, one-off endpoints, learning purposes
- **CBV**: Complex APIs with shared behavior, REST-style endpoints with multiple HTTP methods, team projects with conventions

### CSS Integration Strategy
- **Base template**: Centralized static file loading in `base.html` for inheritance by all templates
- **Custom properties**: Used CSS variables for consistent color theming across components
- **Bootstrap integration**: Combined custom CSS with Bootstrap for responsive design without conflicts
- **Performance**: Single CSS file minimizes HTTP requests while maintaining organized code structure
