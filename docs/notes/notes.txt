# Data Model Design
- **Models Created**: `Project` and `Task`.
- **Fields**:
    - `Project`: `name`, `description`, `owner`, `created_at`.
    - `Task`: `title`, `description`, `project`, `priority`, `status`, `due_date`, `created_at`, `updated_at`.
- **Relationships**:
    - `Task.project`: A `ForeignKey` to `Project`. This creates a one-to-many relationship where a project can have multiple tasks. `on_delete=models.CASCADE` was chosen so that if a project is deleted, all its associated tasks are also deleted. This keeps the database clean and avoids orphaned tasks.
    - `Project.owner`: A `ForeignKey` to the `User` model. This assigns ownership of a project to a user. `on_delete=models.CASCADE` means if a user is deleted, their projects (and by extension, their tasks) are also deleted.
- **Constraints**:
    - `UniqueConstraint(fields=['project', 'title'], name='unique_task_title_in_project')` in the `Task` model ensures that no two tasks within the same project can have the same title. This prevents duplicate tasks.
    - `ordering = ["name"]` in `Project` and `ordering = ["status", "-priority", "due_date", "-created_at"]` in `Task` provide default sorting for querysets, which is useful for consistent presentation.
- **Seeding Data**:
    - A superuser was created to own the projects.
    - Two projects were created: "Website Redesign" and "Mobile App Development".
    - Several tasks were created for each project with different priorities, statuses, and due dates to simulate a real-world scenario.
    - A duplicate task was attempted to be created to test the `UniqueConstraint`.

# Assignment 4 - Django Views Implementation

## Why I Wrote Two Views
- **HttpResponse View (task_stats)**: Demonstrates manual HTML construction without Django's template system. This shows the low-level approach where you have complete control over the HTML output but must handle everything manually.
- **render() View (task_board)**: Uses Django's template system with context passing. This is the preferred Django approach as it separates logic from presentation and enables template inheritance.

## Differences Between HttpResponse and render()
- **HttpResponse**: Returns raw HTML strings constructed in Python. Requires manual HTML escaping and styling. Good for simple responses or API endpoints. Less maintainable for complex pages.
- **render()**: Uses Django templates with context dictionaries. Supports template inheritance, filters, tags, and automatic HTML escaping. More maintainable and follows Django best practices.

## URL and Template Decisions
- **Separate URLs**: Created distinct URLs (/tasks/stats/ and /tasks/) to clearly demonstrate both approaches working independently.
- **Template Inheritance**: Used base.html with {% block %} structure to maintain consistent navigation and styling across all pages.
- **{% for %} with {% empty %}**: Implemented in all list templates to gracefully handle empty querysets with user-friendly messages.
- **Context Strategy**: Passed multiple querysets in render() view to organize tasks by status, enabling the kanban board layout.

## Key Learning Points
- HttpResponse requires manual work but gives complete control
- render() leverages Django's powerful template system for cleaner, more maintainable code
- Both approaches can use the same underlying data and business logic
- Template inheritance eliminates code duplication across pages

# Assignment 6 - Base CBVs vs Generic CBVs Implementation

## Difference Between Base CBVs and Generic CBVs

### Base CBVs (inheriting from View)
- **Manual Implementation**: Must implement get(), post(), etc. methods explicitly
- **Explicit Queries**: Write all database queries manually (Task.objects.count(), Task.objects.filter())
- **Custom Context**: Create context dictionaries with custom variable names
- **Full Control**: Complete control over request/response cycle and data processing
- **More Code**: Requires more boilerplate code but maximum flexibility

### Generic CBVs (ListView, DetailView, CreateView)
- **Automatic Implementation**: Django handles common patterns automatically
- **Built-in Queries**: Automatic queryset handling based on model attribute
- **Standard Context**: Uses default context names (object_list, object) or custom context_object_name
- **Convention-based**: Follows Django conventions for template naming and behavior
- **Less Code**: Minimal code required, built-in pagination, form handling, etc.

## Why Generic Views Reduce Boilerplate

### Before (Function-based or Base CBV):
```python
def task_list(request):
    tasks = Task.objects.all().order_by('status', '-priority')
    paginator = Paginator(tasks, 10)
    page = request.GET.get('page')
    tasks = paginator.get_page(page)
    context = {'tasks': tasks}
    return render(request, 'tasks/task_list.html', context)
```

### After (Generic ListView):
```python
class TaskListView(ListView):
    model = Task
    paginate_by = 10
    ordering = ['status', '-priority']
```

- **Automatic pagination**: No need to write pagination logic
- **Queryset handling**: Django automatically queries Task.objects.all()
- **Context creation**: Automatic context with 'object_list' or custom name
- **Template selection**: Follows convention (app/model_list.html) or custom template_name

## Why Refactoring URLs Improves Maintainability

### Before Refactoring (all URLs in project-level):
- All app URLs mixed together in main urls.py
- Hard to find and modify specific app routes
- URL naming conflicts between apps
- Difficult to reuse apps in other projects

### After Refactoring (with include()):
- **Separation of Concerns**: Each app manages its own URLs
- **Modularity**: Apps are self-contained with their URL patterns
- **Namespace Support**: Prevents URL name conflicts
- **Reusability**: Apps can be easily moved between projects
- **Maintainability**: Easier to find and modify URLs for specific features
- **Team Development**: Different developers can work on different apps independently

### URL Structure Benefits:
```python
# Project-level: Clean and focused
urlpatterns = [
    path('admin/', admin.site.urls),
    path('', home, name='home'),
    path('tasks/', include('tasks.urls')),  # Delegates to app
]

# App-level: Complete control over app routes
urlpatterns = [
    path('cbv/', TaskListView.as_view(), name='task_list_cbv'),
    path('cbv/stats/', TaskStatsView.as_view(), name='task_stats_cbv'),
]
```

### Base CBV (TaskStatsView):

# Assignment 7 - Search/Filtering and Aggregations Implementation

## Filtering vs Aggregation Concepts

### Filtering (Narrowing Data)
- **Purpose**: Reduces the number of rows returned from a queryset based on conditions
- **Django Methods**: `.filter()`, `.exclude()`, `.get()`
- **SQL Equivalent**: WHERE clause conditions
- **Our Implementation**: Multi-field search using Q() objects across task title, description, and project name
- **Result**: Returns a subset of Task objects that match the search criteria

### Aggregation (Summarizing Data)
- **Purpose**: Computes summary values across groups of data (counts, sums, averages)
- **Django Methods**: `.count()`, `.aggregate()`, `.annotate()` with `Count()`, `Sum()`, `Avg()`
- **SQL Equivalent**: GROUP BY clauses with aggregate functions
- **Our Implementation**: Overall totals and grouped counts by status, priority, and project
- **Result**: Returns computed summary statistics rather than individual objects

## Specific Aggregation Summaries in Our Project

### Overall Aggregations (Single Values)
- **Total Tasks**: `Task.objects.count()` - Simple count of all tasks in system
- **Completed Tasks**: `Task.objects.filter(status=Status.DONE).count()` - Count with filter condition
- **Overdue Tasks**: Complex filter with date comparison and status exclusion for actionable overdue items

### Grouped Aggregations (Counts by Category)
- **Tasks by Status**: `Task.objects.values('status').annotate(count=Count('id'))` - Groups tasks by status field and counts each group
- **Tasks by Priority**: `Task.objects.values('priority').annotate(count=Count('id'))` - Groups by priority level with count
- **Tasks by Project**: `Project.objects.annotate(task_count=Count('tasks'))` - Counts tasks per project using reverse relationship

## Query Optimization Techniques Used
- **select_related('project')**: Prevents N+1 queries when displaying task project names in list view
- **Q() Objects**: Enables OR logic for multi-field search across unrelated fields
- **Lazy Evaluation**: QuerySets not executed until template iteration, allowing efficient chaining of filters and annotations
